AML 双通道现场演示
详细实施规格

目标：现场创建两笔企业付款。付款 A 通过制裁筛查并执行，随后作为八笔关联交易之一被全量夜间监控建案并交给 Sarah；付款 B 因潜在制裁名单匹配，在执行前被暂挂。本文档给出可直接实施的状态、时间、API、数据、并发和测试设计。

01

已冻结的技术决策

Approved direction
保留核心业务链；新增独立 Demo Scenario 编排层。

Sanctions、R1–R4、Case Consolidation、Sarah 工作台和 AI draft 继续作为唯一业务实现。Demo 层只控制数据准备、虚拟时间、调用顺序、状态恢复和页面导航，不复制规则。

Non-negotiable
不通过数据库猜测状态，不事后覆写付款时间。

场景状态写入专表；付款时间通过显式执行上下文进入业务服务；系统审计事件使用业务时间，人工事件使用真实时间。

领域最终决定原因
Reset全量 TRUNCATE + 选择性确定性 reseed宁可接受数秒等待，也不承担残留数据和定向 DELETE 条件漂移。
场景状态持久化 demo_scenario_state，P0支持刷新恢复、锚点识别、幂等、并发与可诊断错误。
虚拟时间显式 PaymentExecutionContext / 方法重载正式 API 不接受任意时间；不使用 ThreadLocal，不在保存后 UPDATE。
夜间监控继续全量扫描；Demo profile 禁用自动 cron保留真实故事，同时消除演示后台任务竞争。
付款 A 单独状态承认 R4=15、GREEN；完整模式才成为 REDNG 在高风险清单中；Guard 只能保护执行顺序，不能改变规则事实。
场景定义Fixture 只定义数据；预期规则只存在于测试避免生产输入同时充当测试预言机。
前端新增一个 /demo.html Presenter Console业务页面不承担演示状态机；现有 Sarah 页面只做局部增强。
02

目标流程与业务事实

STEP 01

创建付款 A

ACME → Sahel Logistics NG，£26,000。制裁筛查无潜在匹配，RELEASED，业务时间为前一天 16:52。

STEP 02

补齐当日活动

以后端保存的锚点付款为准，创建其余7笔上下文交易，形成16:10–17:05的完整窗口。

STEP 03

运行全量监控

按当天02:00 as-of扫描全部客户；唯一新增案件必须是 ACME，规则输出必须为实际计算结果。

STEP 04

Sarah 调查

同一 txnRef 出现在案件时间线；Sarah 查看证据、编辑 AI draft、作出内部升级决定。

STEP 05

创建付款 B

Vladmir Petrov + DOB + nationality。姓名产生潜在匹配，付款 HELD 且未执行。

付款 A 的准确解释

它通过的是制裁筛查，不是所有风险判断。若此时单独运行 AML 规则，会因 NG 命中 R4，得到15分 GREEN 信号；夜间完整活动使 R1–R4 同时出现并形成 RED 高优先级案件。

付款 B 的准确解释

0–1 数值是姓名相似度，不是身份概率。DOB 和 nationality 只增强人工复核证据，不参与当前 similarity 计算。最终画面应是 Potential match / Held / Not executed。

03

架构与职责边界

组件职责不得承担
DemoScenarioController暴露 demo-only typed API；将 HTTP 错误映射为409/404。不创建实体，不判断规则，不推导状态。
DemoScenarioService锁状态行、校验步骤、调用业务服务、验证不变量、提交下一状态。不复制 sanctions、rule 或 case 逻辑。
DemoScenarioStateRepository读取唯一场景状态；提供带锁读取。不通过交易数量猜测当前步骤。
DemoDataSeedService客户、随机基线、ACME 特殊基线、其他队列案件的确定性创建。不推进现场场景。
AcmeScenarioFixture纯数据：金额、方向、偏移、对手方、国家、anchor 标识。不保存 expected rules、score 或 casesRaised。
SyntheticTransactionFactory根据完整 spec 构造一致的 synthetic TransactionEntity。不访问 repository，不决定何时创建。
SanctionsScreeningService正式付款创建、名单匹配、RELEASED/HELD 状态和 sanctions hit。不读取 scenario state。
MonitoringRunService按 as-of 全量评估并返回 typed run result。不依赖 demo 表；调度开关由 profile 配置。
CaseConsolidationService基于规则命中创建/更新案件并产生 CASE_OPENED audit。不硬编码 ACME 或演示分数。
调用方向：DemoScenarioService → 正式业务 Service → Repository。业务 Service 绝不反向依赖 DemoScenarioService，从而保证演示能力不会污染生产规则。
04

数据库状态机与迁移

新增 Flyway migration

CREATE TABLE demo_scenario_state (
    scenario_key       VARCHAR(64) PRIMARY KEY,
    step               VARCHAR(32) NOT NULL,
    customer_id        BIGINT REFERENCES customer(id),
    anchor_payment_id  BIGINT REFERENCES txn(id),
    simulated_as_of    TIMESTAMPTZ,
    case_id            BIGINT REFERENCES case_record(id),
    sanctions_hit_id   BIGINT REFERENCES sanctions_hit(id),
    version            BIGINT NOT NULL DEFAULT 0,
    updated_at         TIMESTAMPTZ NOT NULL
);

CREATE SEQUENCE payment_ref_seq START WITH 1;

表可以存在于通用 schema，但 controller/service 只在 demo profile 注册。Reset 时必须先清 scenario state，再清它引用的业务表，并重置 payment reference sequence。

READY→PAYMENT_A_RELEASED→ACTIVITY_READY→CASE_RAISED→PAYMENT_B_HELD
当前状态允许动作成功后重复调用
READYCreate Payment A保存 anchor ID 和 simulatedAsOf若已成功则返回已保存 Payment A；不新建第二笔。
PAYMENT_A_RELEASEDComplete Activity创建其余7笔，转 ACTIVITY_READY返回已有场景汇总；交易数量不增加。
ACTIVITY_READYRun Monitoring保存唯一 ACME case ID返回已有案件；不重复运行。
CASE_RAISEDCreate Payment B保存 sanctions hit ID返回已有 HELD 结果。
PAYMENT_B_HELDReset回到 READYGET 始终返回最终结果。

每个推进动作在单个事务内通过带锁查询读取状态。合法重试是幂等返回；越级、冲突输入或数据库事实不符合状态时返回 409 Conflict。

05

虚拟业务时间与审计边界

固定业务时间

DEMO_DAY           = LocalDate.now(UTC)
Activity window    = DEMO_DAY-1 16:10 → 17:05
Payment A          = DEMO_DAY-1 16:52
Monitoring as-of   = DEMO_DAY   02:00
Payment B          = live Clock time

其余7笔并非全部发生在 Payment A 之后；场景动作是在数据库中补齐完整当日上下文。口播使用“补齐当天活动”，不使用“后来又发生七笔”。

显式注入机制

record PaymentExecutionContext(
    Instant occurredAt,
    LocalDate fxRateDate
) {}

screenPayment(request)
  → screenPayment(request, liveContext(clock))

demo Payment A
  → screenPayment(request, virtualContext)

FX date、createdAt、executedAt 和 payment audit 全部来自同一 context；禁止调用正式方法后再 UPDATE 时间。

Audit 时间规则

事件时间来源理由
PAYMENT_SCREENED / PAYMENT_RELEASED（A）PaymentExecutionContext.occurredAt模拟业务系统在前一天执行付款。
MONITORING_RUN_COMPLETEDMonitoringRunService.run(asOf) 的 asOf与规则窗口和 run result 保持一致。
CASE_OPENEDCaseConsolidationService 收到的 asOf与 openedAt、alert createdAt 和 SLA 同步。
CASE_VIEWED / AI_DRAFT_* / CASE_DISPOSED / CASE_ESCALATED注入的 live Clock这些是 Sarah 在现场真实执行的人工行为。
PAYMENT_SCREENED / PAYMENT_HELD（B）live Clock第二笔在演示现场即时提交，且没有 executedAt。
AuditService 改造：保留 record(...) 作为 live-clock 入口，增加 recordAt(Instant,...)；两个重载最终委托同一个 private persist 方法，避免 Map/JsonNode 两套构建逻辑继续复制。

接口/类型变更兼容策略

08

前端详细方案

One new surface
/demo.html 是状态机的视图，不是状态的来源。

每次加载先 GET state；每个动作成功后用服务器返回的完整 state 重绘。前端不计算风险分数、不保存唯一 anchor、不硬编码交易编号和监控指标。

Presenter Console

  • 五步 stepper 和明确的虚拟业务时间轴。
  • 当前合法主按钮一个；请求期间立即禁用。
  • Payment A 显示 RELEASED、txnRef、executedAt、No potential match。
  • Activity 显示 API 返回的8笔汇总，不写死金额或比例。
  • Monitoring 显示实际 scan counts 和唯一新案件。
  • Payment B 显示 name similarity、DOB/Nationality EXACT、HELD、Not executed。
  • 最终并排显示 Case raised 与 Payment held。

错误与恢复

  • 409 显示当前服务器步骤，并提供 Refresh state。
  • 场景不变量失败时显示阻断 banner，不继续自动跳转。
  • Reset 显示全量重建 spinner，不假装即时完成。
  • 刷新、前进后退、重复点击后页面必须回到服务器事实。
  • 不使用 alert()；错误信息保留在页面，便于现场说明。

case.html 增强

  • 读取 focusTxnRef 并高亮同一付款。
  • 时间线增加 Status 列。
  • 显示 “Opened by monitoring run” 和 as-of。
  • 保留现有 score breakdown、AI、Disposition、Audit。

现有页面边界

  • index.html 增加 Live Demo 导航；通用按钮仍保留。
  • 场景活跃时通用 Run Monitoring 根据409给出说明。
  • sanctions.html 继续提供可选深挖，但 Demo 不自动跳转。
  • 现有 index 已提供 DOB 和 nationality，无需重复修复。
09

幂等、并发、调度与不变量

事务与锁

  • 状态转换先以 PESSIMISTIC_WRITE 读取唯一行。
  • 付款/交易/案件写入与 step 更新在同一外层事务。
  • 相同已完成动作返回已有结果；不同意图或越级返回409。
  • version 用于检测异常覆盖并支持诊断。

调度与 Guard

  • 新增 application-demo.yml，设置 aml.monitoring.cron: "-"。
  • 正式 profile 继续使用02:00 cron。
  • 场景处于 PAYMENT_A_RELEASED 或 ACTIVITY_READY 时，通用手动 monitoring 返回409。
  • Demo endpoint 直接调用 MonitoringRunService，不经过通用 controller guard。

运行后必须验证的不变量

动作不变量失败处理
Payment ARELEASED；executedAt=虚拟时间；无 sanctions hit；state anchor 指向同一 ID。事务回滚，保持 READY。
Activity完整窗口恰有8笔场景活动；anchor 只出现一次；15笔 supplement 未改变。事务回滚，保持 PAYMENT_A_RELEASED。
MonitoringcasesRaised=1；唯一 case.customerId=ACME；score=sum(alert points)；band=RED。返回 DEMO_SCENARIO_INVARIANT_VIOLATION，不推进状态。
Payment BHELD；executedAt=null；matched source ID 正确；DOB/Nationality detail=EXACT。事务回滚，保持 CASE_RAISED。
R4 保护原因：Payment A 单独运行规则会产生 R4=15 并足以建立 GREEN case。禁用 demo cron 和保护通用 monitoring 是 P0，不是视觉层优化。

工作包具体任务主要文件进入下一步的条件
WP0
Characterize		 在任何结构变更前固定当前行为：非 ACME 客户无窗口 hits；Payment A alone 恰好 R4=15；完整现有故事命中 R1–R4；R3 namespace 无碰撞。 新增 DemoBaselineCharacterizationTest 所有断言在当前代码和固定 seed 42 上稳定通过。

WP2

WP5

Frontend		 新增 Presenter Console；Case focus/status；导航和错误恢复；Held 结果停留在 Demo 页。 static/demo.html、case.html、index.html、app.css 只靠按钮完成全流程；刷新任意步骤可恢复；无手工查找 ID。
WP7

测试矩阵与最终验收

规则与数据 Characterization

  • 非 ACME、无 open case 客户在模拟窗口无 rule hits。
  • Payment A alone 仅命中 R4，points=15。
  • 完整 activity 命中 R1–R4，score 等于 points 之和且 band=RED。
  • ACME supplement 恰有15笔，CP-LEGACY 均为 known。
  • CP-NEW 与随机 baseline ref 无交集。

状态、幂等与并发

  • 合法状态转换成功；所有越级动作返回409。
  • Payment A、Activity、Monitoring、Payment B 各重复调用不重复写。
  • 两个并发 Activity 请求只有一个执行写入。
  • 两个并发 Monitoring 请求只创建一个案件。
  • Reset 后旧 anchor/case/hit 不可恢复。

时间与审计

  • Payment A executedAt、createdAt、payment audits 使用虚拟时间。
  • Monitoring audit、CASE_OPENED、case.openedAt 使用同一 asOf。
  • CASE_VIEWED、AI 和 disposition 使用 live Clock。
  • Demo profile cron 被禁用；正式 profile cron 未被禁用。

制裁与页面证据

  • Vladmir 匹配指定 Vladimir source entry，similarity ≥ threshold。
  • DOB 和 nationality details 均为 EXACT，但不改变 name score。
  • Payment B HELD、executedAt=null，且不进入 AML 时间窗。
  • Case 页面高亮 anchor txnRef；Demo 页面显示同一 txnRef。
Golden-path integration：reset → state READY → Payment A RELEASED → Activity 8 txns → full monitoring 1 ACME RED case → same txnRef in evidence/timeline → Sarah actions → Payment B HELD + null executedAt。

最终演讲顺序

1

“我们用两笔付款展示两种不同的控制结果：一种产生调查案件，一种在执行前暂挂付款。”
